## 0. 프로젝트 컨텍스트

### 목적
FotMob 클론. 구직용 포트폴리오 프로젝트이므로 **기능 개수보다 기술적 판단의 근거가 드러나는 것**이 우선이다.

### 현재 스택
- Next.js App Router / TypeScript / SCSS Module
- React Query (클라이언트 데이터) / Zustand (UI 상태)
- framer-motion, lucide-react, date-fns, axios
- 외부 데이터: football-data.org v4, **무료 플랜 고정. 유료 플랜으로 전환하지 않는다.**

### 데이터 계층 (반드시 유지)
| 경로 | 역할 |
| --- | --- |
| `app/_libs/football/*` | 서버 전용 fetch. `footballServerFetch` 만 사용. API 키는 여기서만 읽는다 |
| `app/api/football/*` | 클라이언트용 프록시 라우트 핸들러. 키 은닉 + 입력 검증 |
| `app/_libs/_apis/*` | 클라이언트 axios + React Query. 반드시 프록시 경유 |
| `app/_libs/_utils/*` | 순수 함수. 외부 의존 없음 |

### 무료 플랜 제약 — 모든 설계의 전제
공식 문서와 가격 페이지 기준이다. 착수 전 한 번 더 확인할 것.

- **분당 10회 요청.** 월 총량이 아니라 분당 한도다. 초과 시 429.
- **스코어와 일정이 지연된다.** 실시간 스코어는 유료 플랜 기능이다.
  지연 폭은 공개돼 있지 않으므로, 경기 중에 직접 호출해 실측한 값을 README 에 기록한다.
- **라인업 · 교체 · 카드 · 스쿼드 · 선수 개별 스탯이 없다.** 선수 평점류 기능은 구현 대상에서 제외한다.
- 12개 대회만 제공. 현재 `SUPPORTED_LEAGUES` 8개는 이 범위 안에 있다.

### 그래서 이 프로젝트가 내세울 것
"실시간"이 아니라 **분당 10회 한도 안에서 다중 사용자 서비스를 성립시킨 캐시 · 요청 설계**다.
README 와 면접에서 이 표현을 쓴다. 지연 데이터를 실시간이라고 쓰지 않는다.

### 요청 예산 (분당 10회를 이렇게 배분한다)
| 용도 | 캐시 주기 | 분당 소모 |
| --- | --- | --- |
| 오늘 경기 전체 (`/v4/matches?date=`) | 60초 | 1 |
| 리그 목록 (`/v4/competitions`) | 24시간 | ≈ 0 |
| 순위표 (리그당) | 10분 | 리그당 0.1 |
| 팀 상세 / 팀 경기 | 10분 | 조회된 팀 수 × 0.1 |
| **여유분 (429 재시도 · 예외)** | — | **최소 3 확보** |

이 표를 넘기는 설계는 채택하지 않는다.

## 외부 API 사용 규칙 (무료 플랜)

- football-data.org 무료 플랜은 **분당 10회** 제한이다. 새 기능을 추가할 때는

- **N개 대회를 for 문으로 각각 호출하지 않는다.** `/v4/matches` 리스트 리소스에

- 429 응답은 정상 시나리오로 취급한다. 예외로 터뜨리지 말고 폴백 데이터를 반환한다.

## Phase 0 — 요청량 최적화 (다른 모든 Phase 의 선행 조건)

**문제**
현재 `getTodayMatchesServer` 는 `SUPPORTED_LEAGUES` 8개를 각각 호출한다.
여기에 `getCompetitionsServer` 1회를 더하면 홈 페이지 캐시 갱신 1회당 **9 요청**이다.
분당 10회 한도에서 여유가 1회뿐이라, 리그 페이지나 팀 페이지를 여는 순간 429 가 난다.

**요구사항**
1. `app/_libs/football/todayMatches.ts` 재작성
   - 8개 루프를 제거하고 `/v4/matches?date=<yyyy-MM-dd>` **단일 호출**로 바꾼다.
   - 응답의 `competition.code` 로 리그별 그룹핑을 수행한다.
     그룹핑 함수는 `app/_libs/_utils/match.ts` 에 순수 함수로 분리한다.
   - `SUPPORTED_LEAGUES` 에 없는 대회는 필터링한다.
   - 반환 타입(`TodayMatchesResponse`)은 유지해서 호출부를 건드리지 않는다.
   - `?competitions=PL,SA,...` 파라미터도 알려져 있으나 공식 필터 표에는 없다.
     쓰기 전에 실제 응답으로 동작을 확인하고, 확인되면 사용해 전송량을 더 줄인다.
2. 폴백 정책 조정
   - 단일 호출이므로 "리그 하나만 실패" 시나리오가 사라진다.
   - 호출 실패 시 빈 `leagues` 배열을 반환하고, 화면은 `ErrorNotice` 로 안내한다.
3. `footballServerFetch` 에 429 처리 추가
   - 429 응답이면 `FootballApiError` 대신 전용 `RateLimitError` 를 던진다.
   - 응답 헤더에 대기 시간 정보가 있으면 에러에 담아 로그에 남긴다.
   - 호출부는 이 에러를 잡아 폴백한다. 재시도 루프를 돌리지 않는다.
     (한도 초과 상황에서 재시도는 상황을 악화시킬 뿐이다.)

**완료 조건**
- [ ] 홈 페이지 캐시 갱신 1회당 외부 API 호출이 2회 이하다. (서버 로그로 확인)
- [ ] 기존 화면 동작과 표시 내용이 이전과 동일하다.
- [ ] 홈 → 리그 순위 → 팀 상세를 1분 안에 연속으로 눌러도 429 가 나지 않는다.

**README 에 남길 것**
9 → 2 요청으로 줄인 전후 비교. 숫자가 있는 개선은 그 자체로 설명이 된다.

## Phase 1 — 자동 갱신 스코어

> 무료 플랜은 스코어가 지연된다. 이 Phase 는 "실시간"을 만드는 것이 아니라
> **갱신을 낭비 없이 수행하는 구조**를 만드는 것이다. 명칭과 문구를 그에 맞춘다.

**요구사항**
1. `app/_hooks/useMatchPolling.ts` 신설
   - 경기 목록에 `IN_PLAY` 또는 `PAUSED` 가 하나라도 있을 때만 폴링을 활성화한다.
     (`status=LIVE` 는 이 둘을 합친 편의용 필터값이다.)
   - **폴링 간격은 서버 캐시 주기(`REVALIDATE.live`, 60초)보다 짧게 잡지 않는다.**
     더 자주 불러도 같은 캐시를 받을 뿐이라 낭비다. 기본 60초로 시작한다.
   - 전 경기가 `FINISHED` / `POSTPONED` / `CANCELLED` 면 폴링을 완전히 중단한다.
   - Page Visibility API 로 탭이 백그라운드면 폴링을 멈추고, 복귀 시 즉시 1회 refetch 한다.
   - 폴링 간격 상수는 `_constants/football.ts` 에 둔다. 컴포넌트에 하드코딩하지 않는다.
2. `app/api/football/matches/route.ts` 신설
   - `date` 쿼리 파라미터(`yyyyMMdd`)를 정규식으로 검증하고, 형식이 틀리면 400 을 반환한다.
   - Phase 0 의 단일 호출 함수를 재사용한다. `revalidate: REVALIDATE.live` 적용.
   - 429 는 500 이 아니라 빈 결과 + 상태 플래그로 응답한다.
3. `app/_libs/_apis/matches/{apis,queries}.ts` 신설
   - `useTodayMatches(date, initialData)`. 서버 컴포넌트가 넘긴 데이터를 `initialData` 로
     주입해 최초 렌더 시 추가 요청이 없게 한다.
4. `TodayMatches` 를 위 훅 기반으로 전환
   - 서버에서 받은 `leagues` 를 `initialData` 로 넘긴다.
   - 스코어가 변경된 경기 행은 배경 플래시 애니메이션을 1회 재생한다(framer-motion).
   - 이전 스코어 비교 로직은 `app/_libs/_utils/match.ts` 에 순수 함수로 추가한다.
5. 진행 중 경기 표시
   - 진행 시간(`minute`)과 함께 갱신 인디케이터를 표시한다.
   - **레이블은 "LIVE" 가 아니라 "자동 갱신" 또는 마지막 갱신 시각으로 한다.**
   - 데이터 지연 안내 툴팁을 한 곳에 둔다. ("무료 API 특성상 스코어가 지연될 수 있습니다")

**하지 말 것**
- 전역 인터벌 하나로 모든 데이터를 갱신하지 않는다. 순위표 · 팀 정보는 폴링 대상이 아니다.
- 폴링 간격을 캐시 주기보다 짧게 잡지 않는다.
- UI 어디에도 "실시간" 이라고 쓰지 않는다.

**완료 조건**
- [ ] 라이브 경기가 없는 날에는 네트워크 탭에 반복 요청이 잡히지 않는다.
- [ ] 탭을 백그라운드로 두면 요청이 멈추고, 돌아오면 즉시 1회 발생한다.
- [ ] 브라우저 탭을 5개 열어도 외부 API 호출은 분당 1회를 넘지 않는다. (서버 로그로 확인)
- [ ] 스코어가 바뀐 행에만 플래시가 뜬다.

**README 에 남길 것**
동시 접속자가 늘어도 외부 API 호출량이 늘지 않는 이유를 다이어그램 한 장으로 정리한다.
브라우저 N개 → 프록시 라우트 → 60초 캐시 → 외부 API 1회. 이 프로젝트의 핵심 설명 포인트다.
실측한 데이터 지연 폭도 함께 기록한다.

## Phase 2 — 내 팀 · 개인화

**목표**
껍데기만 있는 `app/my-teams` 라우트를 실제 기능으로 만들고, 홈을 개인화한다.
개인화는 **추가 요청 없이** 이뤄져야 한다. 무료 플랜에서 개인화가 성립하는 이유가 여기 있다.

**요구사항**
1. `app/_stores/useFavoriteStore.ts` 신설
   - Zustand `persist` 미들웨어로 localStorage 에 저장한다.
   - 저장 대상: 팀 `{ id, name, crest, code }`, 리그 `{ code, name }`.
   - `toggleTeam`, `toggleLeague`, `isFavoriteTeam`, `isFavoriteLeague` 를 제공한다.
2. 하이드레이션 처리
   - `persist` 는 서버 렌더 시점에 빈 상태이므로 마크업 불일치가 발생한다.
   - `useHasHydrated` 훅을 만들어, 하이드레이션 완료 전에는 개인화 영역을
     스켈레톤으로 렌더한다. `suppressHydrationWarning` 으로 덮지 않는다.
3. 홈 개인화
   - 서버 컴포넌트는 기존대로 **전체 데이터 한 벌**을 가져온다.
   - 클라이언트에서 즐겨찾기 기준으로 **정렬 · 필터만** 수행한다.
     사용자마다 서버 요청이 갈라지면 캐시 적중률이 무너지고 곧바로 429 로 이어진다.
   - 즐겨찾기 팀의 경기를 "My Matches" 섹션으로 최상단에 고정한다.
4. 팀 상세 헤더(`TeamDetailHeader`)와 리그 헤더에 별 토글 버튼을 추가한다.
5. `app/my-teams/page.tsx` 구현
   - 즐겨찾기 팀 목록, 각 팀의 다음 경기와 최근 폼(W/D/L)을 함께 보여준다.
   - **이미 받아온 오늘 경기 데이터로 채울 수 있는 부분은 추가 요청 없이 채운다.**
   - 즐겨찾기가 비어 있을 때의 빈 상태 화면을 만든다.

**완료 조건**
- [ ] 새로고침해도 즐겨찾기가 유지된다.
- [ ] 콘솔에 하이드레이션 불일치 경고가 없다.
- [ ] 즐겨찾기가 0개일 때 홈이 기존과 동일하게 동작한다.
- [ ] 즐겨찾기를 추가해도 외부 API 요청 수가 늘지 않는다.

## Phase 3 — AI 매치 프리뷰

**목표**
AI 를 붙였다는 사실이 아니라 **비용 · 지연 · 실패를 어떻게 통제했는지**가 드러나게 만든다.
무료 플랜에서 얻을 수 있는 데이터(경기 결과 · 순위 · 일정)만으로 성립하는 기능이다.

**요구사항**
1. `app/api/ai/preview/route.ts` 신설
   - 입력: `matchId`.
   - 서버에서 양 팀의 최근 5경기 폼, 현재 순위, 상대 전적을 조회해 프롬프트를 구성한다.
     **클라이언트가 보낸 텍스트를 그대로 프롬프트에 넣지 않는다.** `matchId` 만 신뢰한다.
   - 프롬프트 구성에 필요한 데이터는 **이미 캐시된 것을 우선 재사용**한다.
     AI 기능 때문에 football-data 요청이 늘어나면 안 된다.
   - 응답은 스트리밍으로 내려보낸다.
2. 캐싱
   - 같은 `matchId` 에 대해 반복 호출하지 않는다. 생성 결과를 캐시하고
     경기 상태가 바뀌기 전까지 재사용한다.
   - 캐시는 Next 의 `unstable_cache` 또는 라우트 세그먼트 캐시로 구현한다.
3. 프롬프트 설계
   - 출력은 3~4문장 프리뷰 + 관전 포인트 2개로 고정한다.
   - **주어진 데이터에 없는 사실(부상, 이적, 라인업, 감독 발언)을 만들어내지 않도록 명시한다.**
     무료 플랜에는 라인업 데이터가 없으므로 특히 중요하다.
   - 프롬프트는 `app/_libs/ai/prompts.ts` 에 분리한다. 라우트 안에 문자열로 박지 않는다.
4. `MatchPreview` 컴포넌트
   - 스트리밍 텍스트를 점진적으로 렌더한다. 로딩 중에는 스켈레톤을 보여준다.
   - **실패하면 이 섹션만 조용히 사라지고 나머지 화면은 정상 동작한다.**
     에러 문구로 화면을 채우지 않는다.
   - "AI 생성 내용" 표기를 명확히 한다.
5. 팀 상세의 다음 경기 영역과 경기 행 확장 시점에 노출한다.

**하지 말 것**
- 클라이언트에서 AI API 키를 사용하지 않는다.
- 목록 화면에서 경기마다 자동 호출하지 않는다. 사용자가 펼쳤을 때만 호출한다.

**완료 조건**
- [ ] 같은 경기를 여러 번 열어도 생성 요청은 1회만 발생한다.
- [ ] AI API 를 강제로 실패시켜도 페이지 나머지가 정상 렌더된다.
- [ ] 네트워크 탭에서 응답이 스트리밍으로 들어오는 것이 확인된다.
- [ ] AI 기능을 켜고 끄는 것이 football-data 요청 수에 영향을 주지 않는다.

## Phase 4 — 시각화와 품질

**요구사항**
1. 라운드별 순위 변동 라인 차트
   - **이미 받아온 전체 경기 결과로 라운드별 순위를 직접 계산한다.** 추가 요청 없음.
   - 계산 로직은 `app/_libs/_utils/standings.ts` 에 순수 함수로 둔다.
   - 무료 플랜에서 선수 스탯을 못 쓰는 대신, 계산으로 만들어내는 데이터가 이 프로젝트의
     차별점이 된다. 이 점을 README 에 명시한다.
2. 팀 폼 스트릭(W/D/L) 시각화, 잔여 일정 난이도 지표. 역시 계산으로 만든다.
3. 테스트
   - `_libs/_utils/*` 순수 함수에 Vitest 단위 테스트를 붙인다.
     특히 순위 계산과 승/무/패 판정은 경계 케이스(무승부, 중립 경기, 미종료)를 포함한다.
   - Playwright 로 핵심 흐름 2~3개만 E2E 를 작성한다(홈 진입 → 리그 순위 → 팀 상세).
   - E2E 는 실제 API 를 때리지 않는다. 응답을 목킹한다. (한도 소모 방지)
4. 접근성
   - 키보드만으로 모달 열기/닫기, 날짜 변경, 리그 접기/펴기가 가능해야 한다.
   - 모달에 포커스 트랩을 넣고, 닫을 때 트리거 요소로 포커스를 되돌린다.
5. 성능
   - `@next/bundle-analyzer` 로 번들을 점검한다.
   - 홈을 섹션 단위 `Suspense` 로 쪼개 스트리밍한다.
   - Lighthouse 점수를 측정해 README 에 기록한다.

## 진행 규칙

- 한 번에 한 Phase 만 진행한다. Phase 0 은 반드시 먼저 끝낸다.
- Phase 착수 전에 현재 코드의 관련 파일을 먼저 읽고, 기존 컨벤션을 따른다.
- 새 기능을 제안할 때는 **분당 요청 소모량을 함께 계산해서 제시한다.**
- 새 의존성을 추가할 때는 이유를 먼저 말하고 승인을 받는다.
- 완료 조건을 스스로 체크했다고 보고하지 말고, 확인 방법을 알려준다.
